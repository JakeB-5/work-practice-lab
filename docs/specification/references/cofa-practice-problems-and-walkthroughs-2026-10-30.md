## 문서 범위

이 대화에서 생성한 두 예시 문제, 풀이 시나리오, 담당자에게 할 질문, AI 지시 예시, 범위 조절, 검증 사례, 제출 및 사후 질의응답, 평가축과의 대응, 준비 방법을 모았다. 대화의 설명과 예시는 생략하지 않고 수록했으며, 복사해 사용할 수 있도록 쓰기 블록 표기만 일반 Markdown으로 바꿨다.

두 문제는 모두 **비공식 창작 연습 과제**다. 시간 제한, 담당자 답변, 데이터와 요구사항, 풀이 및 사후 답변은 연습을 위한 가정이다. 공식 기출문제나 공식 모범답안이 아니며 특정 점수를 보장하지 않는다.

첫 번째 문제는 기술적 안정성과 검증을 강조한다. 두 번째 문제는 사용자의 요청에 따라 모호한 업무 요청에서 필요를 발견하고 서비스의 범위를 정하는 과정에 더 무게를 뒀다. 첫 예시에 대한 설명과 한계도 함께 보존했다.

마지막 절의 280~290점 언급은 앞선 대화의 비공식 평가에 관한 것이며, 공식 배점이나 합격 기준이 아니다. 본 문서는 실제 프로그램 구현이나 테스트 실행 결과를 기록한 것이 아니라, 연습 문제와 가상의 수행 시나리오를 기록한 것이다.

## 1. 예시 문제 1 — 장비 대여 예약 서비스

**“장비 대여 예약 서비스”를 만드는 문제로 해보겠습니다.** 기능 자체는 익숙하지만, 필요한 업무 규칙을 발견하고 AI의 설계를 조절하며 결과를 검증하는 능력이 드러나는 과제입니다.

Cofa가 공개한 기준은 **기술: 제대로 작동하는 결과물, 의도: 목표·제약 설정과 AI 지휘, 인지: 선택 이유와 실패 조건 이해**입니다. 결과물뿐 아니라 협업 기록과 사후 답변도 확인합니다. 아래는 이를 참고해 만든 **비공식 연습 문제와 가상의 풀이 시나리오**입니다. 시간과 요구사항은 제가 설정했습니다. [공식 평가 기준](https://www.getcofa.com/ko) · [평가 진행 방식](https://www.getcofa.com/ko/probe)

**1. 처음 받는 문제는 이 정도입니다**

촬영 장비 대여 예약 서비스

당신은 사내 콘텐츠팀을 지원하는 개발자입니다.

직원들은 카메라·마이크·조명을 메신저로 예약합니다. 담당자가 이를 수기로 정리하다 보니, 같은 장비를 같은 시간에 두 사람이 사용하려 하거나 취소된 예약이 계속 남는 일이 발생합니다.

직원이 직접 장비의 예약 가능 여부를 확인하고 예약·취소할 수 있는 작은 웹 서비스를 만들어주세요.

제공 환경:
- 기본 화면과 서버가 연결된 프로젝트
- PostgreSQL 데이터베이스
- 테스트용 직원 로그인 기능
- 장비 목록과 예약 샘플 데이터
- 업무 담당자 역할의 대화 상대

조건:
- 제한 시간: 150분
- 기존 로그인 기능을 활용할 것
- AI 사용 가능
- 구현 범위와 세부 업무 규칙은 담당자에게 확인할 것

제출:
- 실행 가능한 서비스
- 주요 동작을 확인한 테스트 결과
- 중요한 결정과 남은 한계를 적은 짧은 문서

여기서 곧바로 AI에게 “예약 앱 만들어줘”라고 넘기기 전에, **어떤 상황을 막아야 업무 문제가 해결되는지** 확인해야 합니다.

**2. 0~15분: 설계를 바꾸는 질문부터 합니다**

질문을 많이 하는 것이 목적은 아닙니다. 답에 따라 구현이나 완료 기준이 달라지는 질문을 고릅니다.

다음은 **가상의 담당자 답변**입니다.

| 내가 하는 질문 | 담당자의 답변 | 구현에 미치는 영향 |
|---|---|---|
| 가장 먼저 줄여야 하는 문제는 무엇인가요? | 같은 장비의 중복 예약입니다. | 중복 방지를 최우선으로 구현 |
| 예약하면 바로 확정인가요? | 승인 없이 바로 확정입니다. | 승인 화면·승인 상태 제외 |
| 카메라 3대는 같은 종류의 재고인가요, 개별 장비인가요? | 번호가 붙은 개별 장비입니다. | 장비별로 예약을 관리 |
| 시간 단위와 최대 대여 시간은요? | 한국 시간, 30분 단위, 최대 4시간입니다. | 입력 규칙과 저장 방식을 결정 |
| 앞 예약이 11시에 끝나면 다음 예약은 11시부터 가능한가요? | 네. 정리 시간은 별도로 두지 않습니다. | 맞닿는 예약은 허용 |
| 취소 권한과 취소 후 처리는요? | 시작 전 본인 예약만 취소하며, 즉시 다시 예약할 수 있어야 합니다. | 서버에서 소유권·시각 검사 |
| 알림·반복 예약도 필요한가요? | 이번에는 필요 없습니다. | 구현 범위에서 제외 |

이후 목표를 자신의 말로 정리합니다.

> “이번에 해결할 것은 개별 장비의 중복 예약입니다. 직원은 가능한 시간을 보고 예약·취소할 수 있어야 합니다. 동시에 요청해도 중복 예약되지 않는 것이 완료 조건입니다.”

**의도가 드러나는 지점은 담당자의 말을 실제 범위와 검증 조건으로 바꾼 부분입니다.**

답을 얻지 못했다면 확정 사실처럼 취급하지 않습니다. 예를 들어 “예약 사이 정리 시간은 없다고 가정하고 구현하며, 확인이 필요함”이라고 남깁니다.

**3. 15~30분: AI에게 설계를 시키되, 선택은 직접 합니다**

이제 AI에게 다음처럼 요청할 수 있습니다.

> “기존 프로젝트의 화면·서버·DB·로그인 구조를 확인해줘. 확인한 업무 규칙을 기준으로 최소 구현안을 제안해줘. 특히 같은 장비에 동시 예약이 들어올 때 중복을 어떻게 막을지 설명해줘. 아직 구현하지 말고, 기존 구조에서 바뀌는 부분과 중요한 실패 조건을 먼저 정리해줘.”

가령 AI가 이렇게 답했다고 합시다.

> “예약 생성 전에 DB에서 겹치는 예약을 조회하고, 없으면 저장하겠습니다. 화면에서도 예약 버튼을 비활성화하겠습니다.”

여기서 사용자가 해야 하는 판단은 다음과 같습니다.

> “두 요청이 동시에 조회하면 둘 다 ‘예약 없음’을 볼 수 있지 않나? 화면의 버튼 상태와 별개로 서버와 DB에서 중복을 막는 방법이 필요해.”

이것이 **AI의 설명을 이해하고 실패 상황을 제기하는 행동**입니다.

이 문제에서는 예약이 30분 단위이므로 다음 설계를 선택할 수 있습니다.

- 10:00~11:00 예약은 **10:00 슬롯과 10:30 슬롯**을 차지합니다.
- DB는 **같은 장비의 같은 슬롯을 두 예약이 차지하지 못하도록** 제한합니다.
- 예약 기록과 모든 슬롯은 한 번에 저장합니다. 하나라도 충돌하면 전체 저장을 취소합니다.
- 취소할 때도 예약 상태 변경과 슬롯 해제를 한 번에 처리합니다.

선택 이유도 설명할 수 있어야 합니다.

> “시간이 30분 단위로 고정돼 있어서 슬롯 방식이 단순합니다. 중복 조회는 친절한 안내에 쓰고, 최종 중복 방지는 DB가 보장하게 하겠습니다. 나중에 분 단위 자유 예약이 필요해지면 이 설계는 다시 검토해야 합니다.”

이 방식이 모든 예약 시스템의 정답은 아닙니다. **이번 업무 조건에 맞는 선택이라는 점이 중요합니다.**

**4. 30~105분: 핵심 흐름부터 만들고, 중간 결과로 방향을 조정합니다**

구현 순서는 다음처럼 잡습니다.

| 구간 | AI에 맡길 작업 | 내가 확인할 내용 |
|---|---|---|
| 30~60분 | 예약 생성과 DB 중복 방지, 관련 테스트 | 동시 요청에서도 하나만 성공하는가 |
| 60~85분 | 장비·시간 선택 → 예약 → 결과 표시 | 직원이 실제로 예약을 끝낼 수 있는가 |
| 85~105분 | 본인 예약 취소, 권한 검사, 오류 안내 | 취소한 슬롯이 풀리는가, 다른 사람은 취소할 수 없는가 |

AI에게는 “모두 완성한 뒤 알려줘”보다 **의미 있는 구간의 실행 결과를 확인하도록** 맡깁니다.

예를 들어 첫 구간에서는 다음과 같이 요청합니다.

> “예약 생성부터 구현해줘. 두 요청을 동시에 보내는 테스트를 포함하고, 응답 결과뿐 아니라 DB에 남은 예약과 슬롯 수도 확인해줘. 실패하면 예약이나 슬롯 일부만 남지 않아야 해.”

화면 작업 도중 AI가 실시간 소켓, 알림 시스템, 반복 예약을 제안한다면 이렇게 판단합니다.

> “현재 목표에는 예약 직전 재조회와 서버의 충돌 안내면 충분해. 실시간 화면 동기화와 알림은 제외하고 예약·취소를 완성하자.”

단, 제외한 결과도 알아야 합니다.

> “화면에 보이는 빈 시간이 잠깐 오래된 정보일 수는 있습니다. 그 사이 다른 직원이 예약하면 저장 단계에서 거절하고, 시간을 다시 선택하도록 안내합니다.”

**과설계를 줄인다는 것은 필요한 보장을 없애는 것이 아닙니다.** 이 경우 실시간 화면 갱신은 줄여도, 최종 중복 방지는 유지합니다.

**5. 105~135분: AI의 ‘완료’ 보고를 실제 사례로 확인합니다**

검증 기준은 구현이 끝난 뒤 AI가 만든 테스트 목록만 보고 정하지 않습니다. 앞서 확인한 업무 규칙에서 기대 결과를 직접 도출합니다.

| 검증 상황 | 기대 결과 |
|---|---|
| 카메라 A를 10:00~11:00 예약 | 성공 |
| 같은 카메라를 10:30~11:30 예약 | 거절 |
| 같은 카메라를 11:00~12:00 예약 | 성공 |
| 카메라 B를 10:00~11:00 예약 | 성공 |
| 같은 빈 시간에 두 직원이 동시에 예약 | 정확히 하나만 성공 |
| 다른 직원의 예약 취소 요청 | 거절 |
| 시작 전 본인 예약 취소 후 다른 직원이 예약 | 성공 |
| 10:10 시작 또는 4시간을 초과한 예약 | 거절 |

특히 **맞닿는 시간과 겹치는 시간의 차이**를 직접 확인해야 합니다.

가령 AI가 10:00~11:00과 11:00~12:00도 충돌하도록 구현했다면, 다음처럼 수정 방향을 줍니다.

> “담당자는 앞 예약의 종료 시각부터 다음 예약이 가능하다고 했어. 종료 시각의 슬롯까지 점유하는지 확인해줘. 먼저 이 사례가 현재 실패하는 테스트를 추가한 뒤 수정해줘.”

수정 후에는 해당 테스트뿐 아니라 실제 화면에서도 확인합니다.

- 예약 성공 후 목록에 나타나는지
- 충돌할 때 이유가 이해되게 표시되는지
- 실패했는데 성공 화면으로 이동하지 않는지
- 새로고침해도 예약 상태가 유지되는지

코드가 틀렸다면 고치고, 시간이 부족하다면 장식이나 편의 기능을 줄입니다. **핵심 기능의 실패를 문서에만 적고 완료 처리하지 않는 것**이 중요합니다.

**6. 135~150분: 결과와 판단을 연결해 설명합니다**

제출할 때 긴 보고서가 필요한 것은 아닙니다. 실제 구현과 일치하는 짧은 설명이면 됩니다.

> “예약·취소 흐름을 구현했고, 동시 요청에서도 하나의 예약만 저장되는 것을 확인했습니다. 30분 단위라는 업무 규칙에 맞춰 슬롯을 사용했습니다. 예약과 슬롯을 함께 저장해 일부만 남는 상황을 방지했습니다. 실시간 화면 갱신은 제외했으므로, 조회 후 다른 사람이 예약한 시간은 제출 단계에서 충돌 안내가 나올 수 있습니다.”

여기서 테스트를 실제로 실행하지 않았다면 “확인했다”고 쓰면 안 됩니다. 실행한 범위와 미확인 범위를 구분해야 합니다.

사후 질문에는 다음 정도로 답할 수 있으면 좋습니다.

| 질문 | 이해가 드러나는 답변 예시 |
|---|---|
| 버튼을 비활성화하면 중복 예약을 막을 수 있지 않나요? | 다른 브라우저나 직접 요청을 막지는 못합니다. 최종 제약은 서버와 DB에 있어야 합니다. |
| 트랜잭션만 쓰면 충분한가요? | 일반적인 설정에서 조회 후 저장을 트랜잭션으로 묶는 것만으로 중복이 항상 방지되지는 않습니다. 이 구현은 슬롯의 유일성 제약도 사용합니다. |
| 15분 단위 예약으로 바뀌면요? | 슬롯 크기와 기존 데이터 처리 방식을 검토해야 합니다. 임의의 시각을 허용한다면 시간 구간 자체의 중복을 막는 설계를 고려하겠습니다. |
| AI가 한 일과 본인이 한 일은요? | AI가 코드와 테스트 초안을 작성했습니다. 저는 업무 규칙을 확인하고, 동시 요청의 문제를 제기하고, 범위를 결정하고, 실행 결과를 검증했습니다. |

마지막 답변도 **실제로 그렇게 했을 때만** 성립합니다. 판단 기록을 그럴듯하게 만드는 것보다 작업 중 내린 결정이 결과물에 반영돼 있어야 합니다.

이 시나리오에서 세 평가축에 대응하는 증거는 명확합니다.

| 평가축 | 이 풀이에서 남는 증거 |
|---|---|
| **기술** | 예약·취소가 작동하며, 동시 요청·권한·경계 조건을 실제로 검증함 |
| **의도** | 담당자에게 규칙을 확인하고, 중복 방지를 우선하며, 불필요한 기능을 제외함 |
| **인지** | 조회 후 저장의 허점, 슬롯 방식의 선택 이유, 설계가 통하지 않는 조건을 설명함 |

사용자에게 특히 연습 가치가 큰 부분은 **“완료 조건을 먼저 정하고 → 중간 실행 결과로 판단하고 → 마지막에 구현과 일치하게 설명하는 과정”**입니다. 기존 업무에서 보여준 설계 교정 능력을 제한 시간 안의 완성도까지 연결하는 연습이 됩니다.

## 2. 실제 공개 과제와의 관계 및 첫 예시의 한계

**네, 소프트웨어를 만들거나 기존 코드를 수정하는 과제 유형은 공개돼 있습니다. 다만 제가 앞서 만든 예시는 기술적인 검증 쪽에 무게를 많이 둔 편입니다.**

확인된 사례를 구분하면 이렇습니다.

| 공개 사례 | 내용 | 확인 범위 |
|---|---|---|
| **선수 인터뷰 연습 서비스** | 담당자에게 코칭 방식을 물어보고, 선수가 혼자 답변을 연습하고 돌아볼 서비스를 제작 | 영상에서 시연한 과제. 실제 업무의 필요를 본떠 만들었다고 설명 |
| **주문 API 안정성 개선** | 결제 재시도에 따른 주문 중복을 막고, 실패 처리와 테스트를 보완 | 공식 사이트의 **설명용 데모**. 실제 시험 출제 이력까지 확인된 것은 아님 |

각각 [영상 제작자의 인터뷰 원문](https://maily.so/josh/posts/x1zg69d3rqg)과 [공식 개발자 데모](https://www.getcofa.com/brochure-v2/workspace-mock.html)에서 확인할 수 있습니다.

다만 **“트랜잭션·DB 제약을 알아야 모든 Cofa 과제를 잘 푼다”는 뜻은 아닙니다.** Cofa는 개발자뿐 아니라 비개발자용 업무 평가도 제공하며, 직무에 맞는 환경과 과제를 사용한다고 안내합니다. [공식 설명](https://www.getcofa.com/ko/probe)

제가 만든 예약 문제에서는 **중복 예약 방지**를 핵심 목표로 설정했기 때문에 동시 요청과 DB 제약까지 설명했습니다. 반면 영상의 인터뷰 서비스라면 우선 확인할 것은 다음에 가깝습니다.

- 선수들이 인터뷰에서 구체적으로 무엇을 어려워하는가?
- 담당자는 어떤 기준으로 답변을 코칭하는가?
- 선수가 자신의 답변을 어떻게 돌아보면 도움이 되는가?
- 그 과정을 제한 시간 안에 사용할 수 있는 서비스로 만들었는가?

**따라서 영상과 가까운 연습을 원하셨다면, 앞선 예시는 제품의 필요를 발견하는 과정보다 백엔드 안정성 문제를 지나치게 부각했습니다.** 실제에 더 가까운 접근은 짧고 모호한 업무 요청에서 출발해, 필요한 기능과 그에 맞는 기술 수준을 스스로 정하는 것입니다.

## 3. 예시 문제 2 — 신입 매장 직원의 고객 응대 연습

이번에는 **모호한 업무 요청을 받고, 담당자에게 필요한 정보를 알아낸 뒤 작은 서비스를 만드는 과제**로 다시 구성하겠습니다. 기술 선택보다 **누구의 어떤 문제를 해결할지 판단하는 과정**이 중심입니다.

아래는 앞서 확인한 Cofa의 기술·의도·인지 기준을 참고해 만든 **가상의 연습 과제**입니다. 실제 기출문제나 공식 채점표는 아닙니다.

**1. 처음 받는 문제**

신입 매장 직원의 고객 응대 연습을 도와주세요

당신은 생활용품 매장의 교육 담당자와 일하는 개발자입니다.

신입 직원들은 상품 설명을 공부하고도 실제 고객 앞에서는 어떤 질문부터 해야 할지 어려워합니다. 교육 담당자가 모든 신입 직원과 충분히 역할극을 진행하기도 어렵습니다.

직원이 혼자 고객 응대를 연습하고 자신의 답변을 돌아볼 수 있는 웹 서비스를 만들어주세요. 현재 매장에서 사용하는 교육 방식도 자연스럽게 반영되면 좋겠습니다.

제공 자료:
- 상품 6종의 설명 자료
- 교환·반품 정책
- 기존 직원 교육 메모
- 교육 담당자 역할의 대화 상대
- 기본 웹 프로젝트와 AI 사용 환경

제한 시간: 2시간

필요한 기능과 구현 범위는 직접 판단하세요.

실행 가능한 결과물과 함께, 주요 판단 근거와 확인한 내용을 제출하세요.

이 문제를 읽으면 ‘AI 고객과 대화하는 챗봇’을 떠올릴 수 있습니다. 하지만 **챗봇이 실제 교육 문제를 해결하는지는 아직 모릅니다.**

**2. 0~15분 — 담당자에게 업무 장면을 물어봅니다**

첫 질문은 기능 목록을 요청하기보다 실제로 어려웠던 상황을 알아내는 쪽이 좋습니다.

> **나:** “최근 신입 직원이 응대를 어려워했던 사례 하나만 설명해주실 수 있나요?”
>
> **담당자:** “고객이 가습기를 추천해달라고 하면 바로 인기 상품을 설명해요. 어디에서 쓸 건지, 무엇을 중요하게 생각하는지부터 물어야 하는데요.”

이 답변을 받으면 문제의 중심이 ‘상품 지식 부족’과 조금 다르다는 것을 알게 됩니다.

> **나:** “그러면 이번 교육에서는 상품 설명을 잘하는 것보다, 추천 전에 고객의 상황을 알아내는 연습이 더 중요한가요?”
>
> **담당자:** “맞아요. 사용 장소와 불편한 점을 물어보고, 답을 들은 뒤 추천 이유를 연결했으면 좋겠어요.”
>
> **나:** “지금 역할극에서는 어떻게 피드백하시나요?”
>
> **담당자:** “좋았던 표현 하나와 바꿔볼 표현 하나를 짚고, 같은 상황에서 다시 말하게 합니다.”

추가 질문으로 다음 조건을 알아냈다고 가정하겠습니다. **아래 답변도 연습용 설정입니다.**

| 확인할 내용 | 담당자 답변 |
|---|---|
| 언제, 얼마나 연습하나요? | 근무 전 휴대폰으로 5분 정도 |
| 음성이 꼭 필요한가요? | 매장에서는 소리 내기 어려워서 텍스트도 괜찮음 |
| 점수나 직원 순위가 필요한가요? | 필요 없음. 무엇을 바꿀지 알면 됨 |
| 처음부터 모든 상황을 다뤄야 하나요? | 우선 가습기 추천 상황 하나면 됨 |
| 상품·정책에 없는 내용을 말하면요? | 추측해서 안내하지 않고 확인하겠다고 해야 함 |

여기서 목표를 이렇게 정리합니다.

> **“직원이 고객의 필요를 묻고, 그 답에 근거해 추천하는 연습을 5분 안에 한 번 마치고, 피드백을 받아 다시 답할 수 있게 만든다.”**

담당자의 ‘연습 서비스’라는 요청을 **구체적인 사용 흐름과 완료 기준**으로 바꾼 것입니다.

**3. 15~30분 — 무엇을 만들고 무엇을 제외할지 결정합니다**

AI에게 바로 전체 구현을 맡기기 전에 자료와 목표를 연결하게 합니다.

> **나 → AI**
>
> “상품 자료와 교육 메모를 읽고, 방금 확인한 교육 목표를 달성하는 최소 사용 흐름을 제안해줘. 자료에 있는 사실과 네가 제안하는 기능을 구분해줘. 휴대폰에서 5분 안에 끝나야 하고, 피드백 후 다시 답하는 과정이 필요해.”

가령 AI가 다음을 제안했다고 합시다.

> “음성 인식, 고객 성격 선택, 직원별 점수, 관리자 통계, 자유 대화, 상품 추천 기능을 만들겠습니다.”

이때는 기능별로 목표에 필요한지 판단합니다.

> **나:** “이번에는 상황 하나로 시작하자. 음성과 관리자 통계는 제외해. 고객에게 질문하고 답을 받은 뒤 추천하는 과정, 피드백, 재답변에 시간을 쓰자. 담당자가 원하지 않은 직원 순위도 넣지 말자.”

선택한 흐름은 다음 정도입니다.

**고객 상황 확인 → 고객에게 질문 → 고객 답변 확인 → 상품 추천과 이유 작성 → 피드백 → 다시 답하기**

고객 역할에는 미리 정한 상황을 줍니다.

- 침실에서 사용할 예정
- 소음에 민감함
- 세척이 번거로웠던 경험이 있음

이 정보를 처음부터 모두 보여주지는 않습니다. 직원이 관련 질문을 하면 답하도록 합니다. 반면 **피드백을 만들 때는 직원이 실제 대화에서 알아낸 정보만 기준으로 평가**합니다. 묻지도 않았고 전달받지도 않은 정보를 활용하라고 요구하면 부당한 피드백이 됩니다.

**4. 30~80분 — 가장 중요한 경험부터 구현합니다**

먼저 디자인을 완성하기보다 **한 사람이 연습을 끝까지 할 수 있는 흐름**을 만듭니다.

AI에게 다음처럼 맡길 수 있습니다.

> “우선 상황 하나에서 질문·고객 답변·추천·피드백·재답변이 이어지게 구현해줘. 상품 관련 사실은 제공 자료를 근거로 삼아야 해. 피드백에는 사용자의 실제 표현을 인용하고, 잘한 점 하나와 다음에 바꿀 행동 하나를 제시해줘.”

첫 결과가 나왔다고 합시다.

직원이 이렇게 답했습니다.

> “이 제품이 제일 인기 있어요. 이걸로 하세요.”

그런데 서비스가 다음 피드백을 줍니다.

> “친절하고 명확한 추천입니다. 잘하셨습니다!”

여기서 **화면이 작동한다는 이유로 완료하면 안 됩니다.** 교육 목표에 맞지 않는 결과입니다.

사용자가 내려야 할 판단은 다음과 같습니다.

> “고객의 사용 환경을 확인하지 않았는데 좋은 추천이라고 평가하고 있어. 교육 기준과 맞지 않아. 질문으로 확인한 정보가 있는지, 추천 이유가 그 정보와 연결되는지를 보도록 수정해.”

수정된 피드백은 이런 식이어야 합니다.

> “상품을 명확히 제안한 점은 좋습니다. 다만 고객이 어디에서 사용할지 확인하지 않아 추천 이유를 판단하기 어렵습니다. 다음에는 ‘어느 공간에서 사용하실 예정인가요?’라고 먼저 물어보세요.”

반대로 이미 필요한 질문을 했다면 똑같은 조언을 반복해서는 안 됩니다. **실제 대화 내용에 따라 피드백이 달라져야 합니다.**

**5. 80~105분 — ‘교육에 도움이 되는가’를 직접 검증합니다**

검증용 답변을 사람이 먼저 준비하고, 결과가 기대와 맞는지 확인합니다.

| 직접 넣어볼 사례 | 기대하는 반응 |
|---|---|
| 질문 없이 인기 상품부터 추천 | 고객의 필요를 확인하도록 안내 |
| 사용 장소를 물었지만 답변을 무시하고 추천 | 알아낸 정보와 추천 이유를 연결하도록 안내 |
| 필요한 정보를 확인하고 자료에 맞게 추천 | 어떤 질문과 설명이 좋았는지 구체적으로 짚음 |
| 자료에 없는 성능을 확신하며 설명 | 근거가 없음을 지적하고 확인하도록 안내 |
| 짧지만 적절하게 답변 | 길이가 짧다는 이유만으로 낮게 평가하지 않음 |
| 피드백을 반영해 다시 답변 | 실제로 개선된 부분을 구체적으로 설명 |

예를 들어 세척 편의성을 확인한 고객에게 직원이 ‘세척하기 쉬운 제품’을 추천했는데, 서비스가 계속 사용 장소부터 물으라고 한다면 기준을 너무 기계적으로 적용한 것입니다. **상황에 이미 충분한 정보가 있는지도 봐야 합니다.**

또한 휴대폰 화면에서 직접 사용해봅니다.

- 처음 들어온 직원이 무엇을 해야 할지 이해하는가?
- 한 번의 연습이 5분 안에 끝나는가?
- 피드백을 읽고 바로 다시 답할 수 있는가?
- AI 응답이 실패하면 작성한 답변을 잃지 않고 재시도할 수 있는가?

이 과정에서 실제 학습 효과까지 입증한 것은 아닙니다. 이번에 확인한 것은 **의도한 연습 흐름과 피드백이 작동하는지**입니다.

**6. 105~120분 — 시연하고, 선택 이유와 한계를 설명합니다**

마지막 시연에서는 두 가지 답변을 비교하면 좋습니다.

- 고객의 필요를 묻지 않고 추천한 답변
- 질문으로 알아낸 필요를 추천 이유에 연결한 답변

서비스가 두 답변에 **왜 다른 피드백을 주는지** 보여줍니다. 그리고 첫 답변을 수정했을 때 개선이 반영되는지 확인합니다.

사후 질문은 이런 식으로 대비할 수 있습니다.

| 질문 | 답변 예시 |
|---|---|
| 왜 음성 기능을 제외했나요? | 담당자가 텍스트 연습도 가능하다고 했고, 이번 핵심은 질문과 추천의 연결이었습니다. 제한 시간은 피드백과 재연습에 사용했습니다. |
| 왜 점수를 표시하지 않았나요? | 담당자는 직원 비교보다 다음 행동을 알려주는 피드백을 원했습니다. 검증되지 않은 숫자를 추가할 이유가 없었습니다. |
| AI가 잘못된 피드백을 줄 수 있지 않나요? | 가능합니다. 자료를 제공하고 대화 근거를 요구했지만 정확성을 보장하지는 않습니다. 준비한 사례로 확인했고, 확대 전에는 교육 담당자의 추가 검토가 필요합니다. |
| 실제 교육 효과가 있다고 말할 수 있나요? | 아직은 아닙니다. 현재는 작동과 피드백 적합성을 확인했습니다. 효과는 직원의 연습 전후 응대를 담당자가 평가해봐야 합니다. |
| 본인이 내린 중요한 결정은 무엇인가요? | 문제의 중심을 상품 설명에서 고객 필요 파악으로 좁혔고, 피드백 후 재답변을 핵심 흐름으로 정했습니다. 첫 결과가 교육 목표와 맞지 않아 평가 방식을 수정했습니다. |

이 과제에서 좋은 평가를 뒷받침하는 것은 **기능 개수보다 판단과 결과의 연결**입니다.

- **기술:** 직원이 실제로 연습·피드백·재답변을 완료할 수 있습니다.
- **의도:** 담당자에게 업무를 확인하고, 목표에 필요한 기능을 선택하며, 잘못된 AI 결과를 수정합니다.
- **인지:** 무엇을 해결했는지, 왜 그렇게 만들었는지, 아직 무엇을 확인하지 못했는지 설명합니다.

사용자가 기존 업무에서 보여준 **“이 구현이 실제 목적에 맞나?”라고 되묻는 능력**을 그대로 적용할 수 있는 유형입니다. 이번에는 그 판단을 ‘인쇄 품질’ 대신 ‘직원이 응대를 배우는 경험’에 적용하는 것입니다.

## 4. 역량을 더 확인하기 위한 연습 방법

**지금 필요한 것은 더 많은 기능이나 더 복잡한 자동화가 아니라, “내가 이해하고 통제하며, 정해진 조건 안에서 끝낼 수 있다”는 증거입니다.** 앞선 점수가 제 비공식 평가이므로, 아래도 공식 Cofa 공략법이 아니라 현재 평가에서 부족한 근거를 채우는 방법입니다.

특히 **인지 85점과 기술 90점에서 남은 부분**을 확인하는 것이 중요합니다.

| 강화할 부분 | 실제로 할 행동 | 높은 평가를 줄 수 있는 증거 |
|---|---|---|
| **설계 이해** | 완성한 기능의 구조·선택 이유·대안을 AI 없이 설명 | 코드 설명을 외우는 수준을 넘어, 조건이 바뀌었을 때 설계를 수정할 수 있음 |
| **독립적인 검증** | AI가 “완료”라고 하기 전에 본인이 실패 시나리오와 통과 조건을 정함 | 구현이 잘못돼도 통과할 수 있는 검사를 알아채고 보완함 |
| **시간·범위 통제** | 제한 시간과 필수 기능을 정하고, 중간에 포기할 범위까지 결정 | 시간이 부족할 때 핵심 흐름을 완성하고 나머지를 명확히 제외함 |
| **다른 문제로의 전이** | 익숙하지 않은 작은 업무를 같은 방식으로 해결 | 인쇄 도메인 지식이 없어도 필요한 질문과 검증 기준을 도출함 |

**가장 먼저 해볼 것은 이미 만든 ‘주문 스냅샷’ 기능을 본인이 방어해보는 것입니다.** AI를 잠시 끄고 다음 질문에 답해보세요.

- 왜 주문 시점의 데이터를 따로 고정해야 하는가?
- 문서만 복사하고 이미지·폰트는 원본을 참조하면 어떤 문제가 생기는가?
- 스냅샷 생성 중 일부가 실패하거나 같은 요청이 두 번 오면 어떻게 돼야 하는가?
- 다른 설계도 가능한가? 현재 방식은 무엇을 얻고 무엇을 희생하는가?
- 현재 테스트가 전부 통과해도 남을 수 있는 결함은 무엇인가?

모르는 세부사항을 즉시 답해야 한다는 뜻은 아닙니다. **아는 것과 모르는 것을 구분하고, 무엇을 확인하면 판단할 수 있는지 설명하는 능력**도 평가 대상입니다. 답한 뒤 코드와 대조하면 실제 이해의 빈틈을 찾을 수 있습니다.

그다음에는 **작은 기능 하나를 2시간 안에 완성하는 모의 과제**가 좋습니다.

1. **처음 15분:** 사용자 문제, 필수 흐름 하나, 통과 조건, 제외 범위를 본인이 작성합니다.
2. **다음 75분:** AI와 구현하면서 주요 설계 결정과 수정 이유만 기록합니다.
3. **다음 20분:** 직접 정한 실패 시나리오로 검증합니다.
4. **마지막 10분:** 결과를 시연하고, 설계 이유·남은 결함·다음 조치를 설명합니다.

여기서 볼 것은 코드량이 아니라 **완료 여부, 판단의 타당성, 결함을 찾는 능력, 결과를 설명하는 능력**입니다.

이 과정을 익숙한 문제와 낯선 문제에서 반복해 보여준다면, 제 평가에서는 280~290점을 검토할 근거가 생깁니다. **지금 실제 역량이 부족해서 점수를 못 준 부분과, 역량은 있어도 아직 확인하지 못해서 점수를 못 준 부분이 섞여 있습니다. 먼저 그 둘을 구분하는 것이 가장 빠릅니다.**
