## 1. PRD 다음에 Spec이 필요한가

**필요하다. 다만 모든 기능의 상세 Spec을 먼저 완성할 필요는 없다.**

PRD는 “무엇을 왜 만들지”, Spec은 “서로 어떻게 연결하고 어떤 규칙으로 동작할지”, 태스크는 “누가 무엇을 어떤 순서로 완성할지”를 정한다.

이 제품은 여러 역할의 AI, 로컬 파일·프로세스, 제한 시간, 제출 고정, 평가가 연결된다. 각 담당자가 독립적으로 상태 이름과 이벤트 형식, 제출 시점, 역할 권한을 정하면 병렬 작업의 결과를 합칠 때 다시 만들어야 한다.

따라서 다음 순서로 진행한다.

1. **연결 실험과 공통 Spec 초안을 병렬 진행한다.** 실제 지원 여부를 모르는 Codex 동작은 실험으로 확인하고 문서에 반영한다.
2. **공통 계약을 먼저 확정한다.** ID, 상태 전이, 시간, 요청·응답, 이벤트, 오류, 권한, 근거 참조를 맞춘다.
3. **각 기능은 해당 Spec을 확정한 뒤 구현한다.** 편집기 구현이 평가 Spec의 완료를 기다릴 필요는 없다.
4. **같은 계약의 가상 데이터로 UI와 서버를 병렬 개발한다.** 마지막에는 실제 Codex와 실제 파일·프로세스로 연결해 검증한다.

예외 처리, 실패 상태, 허용되지 않는 동작도 Spec에 포함한다. 단순히 PRD의 요구사항을 더 길게 다시 적는 문서는 만들지 않는다.

## 2. 표 읽는 방법과 공통 완료 조건

- **P0:** MVP에 반드시 포함한다. 미완료가 있으면 MVP 완료로 표시하지 않는다.
- **P1:** MVP 이후 확장. P0 출시를 막지 않는다.
- **이후:** 별도 요구사항과 설계가 필요한 범위. 아직 상세 구현량을 확정하지 않는다.
- **선행:** 해당 태스크를 구현·통합하기 전에 완료해야 하는 직접 의존성이다. 선행 태스크의 선행 조건은 생략하지 않고 연쇄 적용한다.
- **W00, W01…:** 의존성으로 계산한 보수적인 착수 묶음이다. 날짜·주차·작업 기간을 뜻하지 않는다.
- **병렬 Wxx:** 같은 W 안의 작업들은 서로 선행 관계가 없어 동시 착수 후보가 된다.
- **단독 Wxx:** 이 계산에서 같은 묶음에 다른 작업이 없다. 전체 프로젝트에서 무조건 한 사람만 일해야 한다는 뜻은 아니다.
- 실제 실행은 앞 묶음 전체가 끝날 때까지 기다릴 필요 없이 **해당 태스크의 선행 조건이 충족되면** 시작할 수 있다.
- 작업 중 발견한 결함은 해당 기능 태스크를 다시 열어 수정한다. 검증 실패를 문서에만 남기고 완료 처리하지 않는다.

### 2.1 공통 완료 조건

1. 태스크에 적힌 산출물과 완료 조건이 충족됐다.
2. 계약·역할 경계·실패 처리가 관련 Spec과 일치한다.
3. 의미 있는 검증 결과와 연결된 근거가 있다. 문서나 낮은 영향의 변경에 기계적인 테스트를 추가하지 않는다.
4. 가상 응답과 실제 실행을 구분한다. 라이브 실행을 요구하는 태스크는 가상 데이터로 완료할 수 없다.
5. 공통 계약이 바뀌면 버전·샘플·영향 받는 소비자를 함께 갱신한다.
6. 실제 구현 시작 시 담당자, 상태, PR/변경 링크, 검증 근거를 추가한다. 현재 모든 태스크는 미착수다.

### 2.2 같은 파일의 동시 수정 제한

의존성이 없다고 같은 파일을 동시에 수정해도 된다는 뜻은 아니다.

| 공동 변경 대상 | 기본 변경 담당 | 다른 작업의 원칙 |
|---|---|---|
| 공통 타입·상태·API/이벤트 | T01 / 플랫폼 | 변경 제안 후 공통 계약부터 반영 |

## 4. 병렬 운영과 중요한 완료 지점

### 4.1 권장 병렬 작업 흐름

최대 네 개의 작업 흐름으로 운영한다면 다음처럼 배분할 수 있다. 이는 작업 분담 제안이며 지금 에이전트나 작업자를 실행했다는 뜻은 아니다.

| 흐름 | 초기 | 공통 계약 확정 후 | 후반 |
|---|---|---|---|
| A — 플랫폼·런타임 | Codex 연결 실험, 공통 계약 조율 | 저장·Codex·세션 상태 | 제출·복구 |
| B — 작업 환경 | 환경 Spec 초안 | 파일·터미널·미리보기 | 검증 실행·근거 수집 |
| C — 화면 | 사용자 흐름·재생 데이터 화면 | 과제·대화·편집·실행 화면 | 제출·질의응답·리포트 |
| D — 과제·평가 | 과제 형식·콘텐츠 초안 | 담당자 사실·평가 기준·평가 Spec | 평가·기준 사례 검토 |

같은 흐름 안에 표시된 모든 작업을 한꺼번에 시작하지 않는다. 각 태스크의 선행 조건을 따른다. 개발 작업을 병렬로 진행하는 것과 제품 내 Codex 실행 동시성을 높이는 것은 별개다. 제품 내 모델 동시성은 PRD의 기본값 1을 유지한다.

### 4.2 반드시 순서를 지켜야 하는 연결

~~~
연결 가능성 검증 + 공통 계약 확정
        ↓
플랫폼 / Codex / 과제 / 작업 환경 / UI 병렬 구현
        ↓
역할별 실제 실행 + 파일·프로세스 상태 통합
        ↓
마감·제출본 고정
        ↓
제출본 검증·근거 수집
        ↓
사후 질문·평가·리포트
        ↓
두 과제 통합 검증·MVP 완료
~~~

평가 로직과 UI는 확정된 샘플 계약으로 앞서 개발할 수 있지만, 실제 평가 완료는 고정 제출본과 실행 근거가 준비된 뒤에만 인정한다.

### 4.3 게이트

| 게이트 | 완료 기준 | 다음에 가능한 일 |
|---|---|---|
| G0 — 연결·계약 | T00.06 + T01.05 | 실연결을 전제로 한 기능별 구현 |
| G1 — 첫 전체 흐름 | T14.01 | 고객 응대 과제의 실제 사용 시연과 개선 |
| G2 — 신뢰성 | T06.06 + T09.05 + T11.07 + T13.05 | 역할 경계·제출·평가·복구 품질 확인 |
| G3 — MVP | T14.05 | 두 과제로 사용할 수 있는 첫 버전 |
| G4 — 후속 확장 | P1별 Spec·완료 조건 | 과제 제작, 비교, 스킬 가져오기 |

T14.05는 모든 P0 태스크를 선행 관계로 포함하도록 구성했다. G1을 통과했다고 전체 MVP가 끝난 것은 아니다.

## 8. 지금 시작할 작업과 보류할 작업

### 바로 시작

1. **T01.01 — 공통 용어·ID·역할·책임 Spec 초안.**
2. **T00.01 — 호스트·인증·버전 진단.**
3. 위 결과가 나오는 대로 T01.02의 상태·시간 Spec과 T00.02의 최소 연결 실험을 병렬 진행.
4. 화면 설계와 과제 초안은 계약에 맞춰 진행하되, 확인되지 않은 런타임 동작을 확정 사실로 쓰지 않는다.

현재 호스트 정보는 PRD에 있지만 실제 개발 시 다시 확인한다. 기존 설치 확인을 실제 연결 검증의 대체로 사용하지 않는다.

### 아직 시작하지 않음

- 공식 점수·합격선 재현.
- 원격 다중 사용자·웹캠 감독·결제·기업용 관리 기능.
- 전체 Spec 완료를 기다리며 기능 구현을 모두 묶어두는 방식.
- 서로 다른 팀이 공통 상태·이벤트·데이터 형식을 별도로 정하는 구현.
- 실제 역할 제한을 확인하지 않은 채 프롬프트만으로 격리가 됐다고 선언하는 구현.

## 9. 계획 유지 규칙

- 태스크 ID는 유지한다. 범위가 커지면 하위 태스크를 추가하고 원래 항목은 묶음 또는 통합 항목으로 바꾼다.
- 의존성을 변경하면 순환 여부와 T14.05의 P0 포괄 여부를 다시 검사한다.
- P0를 P1으로 옮기는 것은 단순 일정 조정이 아니라 PRD의 MVP 범위 변경으로 기록한다.
- 기능 추가 시 PRD ID, Spec, 구현 태스크, 검증 근거를 함께 연결한다.
- 문서에 적힌 호환 버전과 실제 검증 버전이 다르면 결과를 갱신한다.
- 예상 소요 시간은 Spec과 연결 실험 이후 산정한다. 현재 태스크 개수를 인일이나 완료 날짜로 환산하지 않는다.
