## 1. 제품 정의와 목적

사용자가 모호한 업무 요청을 받고, 가상의 업무 담당자에게 질문해 요구사항을 발견하고, AI와 실제 결과물을 만든 다음, 검증·제출·사후 질의응답·회고까지 진행하는 연습 환경을 만든다.

Cofa가 공개한 업무 수행 흐름과 기술·의도·인지의 평가 관점을 참고한다. 공식 서비스의 내부 평가 알고리즘, 비공개 문제, 합격선, 실제 점수를 재현한다고 주장하지 않는다. 별도 제품명으로 제공하고 모든 결과에 “비공식 연습 평가”를 표시한다.

가장 중요한 제품 경험은 다음과 같다.

> 사용자가 “내가 무엇을 만들었나”뿐 아니라 “어떻게 문제를 이해했고, AI의 어떤 제안을 왜 바꿨으며, 무엇을 직접 확인했나”를 실제 작업 기록을 통해 돌아볼 수 있다.

이번 요청의 산출물은 PRD다. 실제 앱 구현, Codex 추론 호출, 연동 성공 확인, 과제 패키지 제작은 후속 개발 단계에 해당한다.

## 2. 배경과 확인된 사실

### 2.1 참고한 공개 환경

Cofa는 직무별 실무 과제 수행, 산출물과 AI 대화·검증 기록 수집, 사후 질의응답, 근거를 포함한 평가 리포트를 공개적으로 설명한다. 개발자 환경에는 코드·문서·테스트가 있는 작업 공간이 포함된다. 이는 제품 흐름의 참고 근거이며 화면을 그대로 복제할 요구는 아니다. [S1]

이 대화에서 작성한 두 문제는 창작 연습 과제다.

1. 장비 대여 예약: 업무 규칙 발견과 기술적 안정성 검증 중심.
2. 신입 직원 고객 응대 연습: 업무 필요 발견, 범위 결정, 제품 경험과 피드백 적합성 중심.

기본 첫 화면에서는 두 번째 과제를 추천한다. 첫 번째 과제는 기술 검증을 더 연습하려는 사용자를 위한 선택지로 둔다.

### 2.2 개발 호스트에서 확인한 사항

2026-10-30에 다음을 읽기 전용으로 확인했다.

| 항목 | 확인 결과 | 해석 |
|---|---|---|
| Codex 실행 파일 | ~/.local/bin/codex | 현재 호스트의 경로. 제품에서는 설정 가능해야 함 |
| CLI 버전 | 0.163.0 | 최초 호환성 검증 대상 버전 |
| 로그인 상태 | ChatGPT 로그인 상태로 표시됨 | 모델 요청 성공이나 잔여 사용량까지 확인한 것은 아님 |
| App Server | 명령 및 stdio 전송 옵션이 제공됨 | 대화형 연결의 우선 후보 |
| 비대화형 실행 | exec, JSON 이벤트 출력, 출력 스키마 옵션 제공 | 진단·일괄 실행을 위한 보조 후보 |

현재 로그인 상태를 활용하는 경로를 우선한다. 앱이 인증 파일의 토큰을 읽어 브라우저로 전달하거나 자체 인증 저장소로 복사하는 방식을 기본 설계로 삼지 않는다.

**로컬 Codex는 실행 도구와 작업 파일이 로컬에 있다는 뜻이다. 모델 추론까지 오프라인이라는 뜻은 아니다.** 실제 요청은 Codex의 계정·모델·네트워크 조건에 영향을 받으며 사용량을 소비할 수 있다.

## 3. 사용자와 사용 범위

### 3.1 초기 사용자

- 한 대의 개발 컴퓨터에서 혼자 연습하는 사용자.
- 자신의 판단, AI 활용, 실행·검증 능력을 함께 개선하려는 사용자.
- 개발 중 시나리오와 역할 프롬프트를 수정하고 반복 확인하는 제작자.

### 3.2 핵심 사용 사례

1. 문제를 고르고 실제로 수행한 뒤 피드백 받기.
2. 담당자에게 질문하는 방식에 따라 요구사항 발견 과정이 달라지는지 연습하기.
3. AI에게 맡길 일과 직접 판단할 일을 나누고 그 흔적을 확인하기.
4. 실패한 시도에서 작업 기록을 확인하고 새 시도로 다시 연습하기.
5. 로컬 Codex를 연결해 화면·스트리밍·중단·복구·평가 흐름을 개발 중 테스트하기.

### 3.3 첫 버전의 가정

- 단일 사용자, 단일 호스트, 동시에 활성화되는 응시 시도는 하나.
- macOS의 현재 개발 환경을 우선 지원.
- 웹 브라우저 UI와 로컬 백엔드를 같은 컴퓨터에서 실행.
- 인터넷 연결과 사용 가능한 Codex 계정이 있음.
- 개인 연습용이며 채용·성적 증명·강한 부정행위 방지 용도로 사용하지 않음.
- 사용자의 기존 저장소를 수정하지 않고 시도별 새 작업 폴더를 생성.

## 4. 목표와 비목표

### 4.1 MVP 목표

- 과제 선택부터 실행, 제출, 사후 질문, 리포트까지 한 번의 흐름을 끝낼 수 있다.
- 업무 담당자, 코딩 도우미, 평가자의 대화 맥락과 접근 범위를 구분한다.
- 코딩 도우미가 실제 파일을 수정하고 명령을 실행할 수 있다.
- 사용자와 AI의 기여, 질문, 파일 변경, 검증 결과를 출처와 함께 남긴다.
- 제출 당시 파일과 기록을 고정하고 같은 근거로 평가를 재실행할 수 있다.
- 새로고침과 연결 장애가 곧 작업 손실로 이어지지 않는다.
- 개발자는 실제 Codex 연결과 기록 재생을 모두 사용해 개발할 수 있다.

### 4.2 MVP 비목표

- Cofa의 공식 점수·순위·합격 가능성 예측.
- 계정 관리, 결제, 기업용 사용자 관리, 원격 다중 사용자 서비스.
- 웹캠 감독, 운영체제 수준의 부정행위 차단.
- 완전한 VS Code 복제, 확장 프로그램 마켓, 원격 개발 환경.
- 음성·영상 인터뷰, 모바일에서 코드를 작성하는 경험.
- 대규모 에이전트 군집이나 자동 문제 생성.
- 제출물의 운영 환경 배포 및 실제 고객 데이터 연동.

## 5. 성공 기준

첫 버전의 성공은 높은 점수를 산출하는지가 아니라, 신뢰할 수 있는 연습 사이클을 제공하는지로 판단한다.

| 구분 | 수용 목표 |
|---|---|
| 전체 흐름 | 두 기본 과제 각각에서 준비 → 수행 → 제출 → 질의응답 → 리포트 완료 |
| 작업 보존 | 저장 완료 표시가 난 메시지·파일이 새로고침 후 유지됨 |
| 평가 근거 | 모든 평가 판정이 실제 근거 ID 또는 “근거 부족” 표시를 가짐 |
| 역할 분리 | 코딩 도우미의 기본 입력과 파일 목록에 비공개 담당자 정보·평가 기준이 섞이지 않음 |
| 제출 일관성 | 제출 이후 작업을 고쳐도 이전 제출본과 평가 근거가 바뀌지 않음 |
| 장애 회복 | Codex 중단·인증 실패·네트워크 오류를 구분하고 작업을 보존함 |
| 사용성 | 처음 쓰는 사용자가 현재 단계와 다음 행동을 화면에서 알 수 있음 |
| 개발 편의 | 기록 재생으로 UI를 점검하고 실제 Codex 연결로 최종 통합 확인 가능 |

모델 답변 속도나 학습 효과는 초기 보장 수치로 두지 않는다. 첫 사용자 시연 후 연습 완료율, 재시도율, 피드백 유용성 응답을 측정한다. 질문 수·토큰 수·코드량 자체를 실력 점수로 사용하지 않는다.

## 6. 사용자 흐름

### 6.1 시작과 환경 확인

1. 사용자가 과제, 모드, 제한 시간을 고른다.
2. 앱이 Codex 실행 가능 여부, 로그인 상태, 버전 호환성, 작업 폴더 생성 가능 여부를 확인한다.
3. 최초 연결 확인은 실제 짧은 요청으로 수행하며 사용량이 발생할 수 있음을 실행 버튼 근처에 표시한다.
4. 과제 템플릿과 의존성을 준비한다. 준비가 끝나기 전에는 시험 타이머를 시작하지 않는다.
5. 사용자가 “시작”을 누르면 문제와 공개 자료가 열리고 타이머가 시작된다.

### 6.2 수행

- 업무 담당자에게 업무 상황·제약·우선순위를 질문한다.
- 발견한 요구를 사용자 메모에 정리한다.
- 필요한 담당자 답변을 선택해 코딩 도우미에게 공유한다.
- 코딩 도우미와 구현하고 직접 파일을 편집하거나 터미널을 사용한다.
- 결과물을 미리보기로 확인하고 테스트를 실행한다.
- 실제 출력과 기대 결과를 비교하며 수정한다.

### 6.3 제출과 사후 질문

- “제출” 클릭 또는 제한 시간 종료로 마감 처리를 시작한다.
- 저장 상태와 실행 중 작업을 정리한 다음 제출본을 고정한다.
- 평가자는 제출본과 작업 기록을 보고 3~5개의 사후 질문을 생성한다.
- 사용자는 구현 이유, 한계, 직접 검증한 내용에 답한다.
- 시험 연습 모드에서는 이 단계의 코딩 도우미를 잠근다.
- 리포트에서 판정·근거·미확인 부분·다음 연습 행동을 확인한다.

### 6.4 재연습

- 이전 시도를 수정하지 않고 새 시도를 만든다.
- 같은 과제로 다시 시작하거나 이전 제출본에서 이어 연습할 수 있다.
- 이어 연습은 선행 맥락을 사용했다는 표시를 붙여 처음 시도와 구별한다.

## 7. 화면 구성

### 7.1 과제 목록

- 제목, 업무 상황, 권장 시간, 연습 초점, 준비 상태.
- 기본 카드: “신입 직원 응대 연습”, “장비 대여 예약”.
- 이전 시도와 결과 보기.
- Codex 연결 상태와 설정 진입.

### 7.2 수행 화면

| 영역 | 내용 |
|---|---|
| 상단 | 과제명, 모드, 남은 시간, 연결·저장 상태, 제출 |
| 왼쪽 | 문제, 공개 자료, 작업 파일 |
| 중앙 | 파일 편집 / 결과 미리보기 탭 |
| 오른쪽 | 업무 담당자 / 코딩 도우미 탭 |
| 하단 | 터미널, 테스트 결과, 작업 기록 |

패널 크기를 조절할 수 있고, 좁은 창에서는 탭으로 전환한다. 사용자 화면에서 프로토콜명·내부 이벤트 필드보다 “답변 중”, “실행 승인 필요”, “저장됨”, “연결 복구 중”처럼 현재 상태를 먼저 보여준다.

업무 담당자와 코딩 도우미는 이름·배지·색을 달리한다. 입력 대상이 명확하게 보이고, 대화 상대를 바꿔도 작성 중인 문장을 보존한다.

### 7.3 제출·질의응답 화면

- 제출 시각, 포함 파일, 실행한 검사, 미저장 또는 중단된 작업 여부.
- 사후 질문별 답변 입력과 임시 저장.
- 제출 파일과 본인 작업 기록은 읽기 전용으로 확인 가능.
- 질문을 건너뛰면 미응답으로 남기며 자동으로 답을 채우지 않는다.

### 7.4 리포트 화면

- 세 평가축별 근거와 보완점.
- 근거 클릭 시 해당 대화, 제출 파일 위치, 실행 기록으로 이동.
- 실제 확인된 결과와 평가 모델의 해석을 구분.
- 비공식 점수와 평가 가능 범위 표시.
- 다음 시도에서 바꿔볼 행동 최대 3개.
- Markdown 리포트와 JSON 근거 목록 내보내기.

### 7.5 개발 모드

- 역할별 입력·출력·오류·Codex 실행 상태 확인.
- 담당자 공개 사실 목록, 평가 기준, 프롬프트 버전 확인.
- 짧은 테스트용 시간, 기록 재생, 실패 상황 재현.
- 비공개 내용을 열거나 시간·설정을 바꾼 시도에는 “개발용 / 조건 변경됨” 표시.
- 개발용 기록을 일반 시험 연습 결과로 조용히 전환하지 않는다.

## 8. 에이전트 역할과 정보 경계

### 8.1 역할 정의

| 역할 | 책임 | 받는 정보 | 허용 작업 |
|---|---|---|---|
| 업무 담당자 | 현업 관점에서 질문에 답함 | 담당자 설정, 선택된 사실, 자신의 대화 | 답변과 확인 질문 |
| 코딩 도우미 | 구현·조사·테스트 지원 | 공개 문제, 공개 자료, 작업 폴더, 사용자가 공유한 맥락 | 파일 수정, 명령 실행, 코드 설명 |
| 평가자 | 제출본과 근거를 평가하고 사후 질문 생성 | 고정된 제출본, 평가 기준, 관련 작업 기록, 사용자 답변 | 평가·질문·리포트 작성 |
| 세션 제어기 | 시간, 상태, 제출, 기록 관리 | 세션 메타데이터 | 애플리케이션 로직으로 처리 |

세션 제어기는 LLM 판단에 맡기지 않는다. 타이머 만료와 제출 여부는 서버 상태가 결정한다. 초기 구현에서는 평가와 사후 질문을 같은 역할 내 단계로 구분하며, 별도 다수 평가 에이전트는 요구하지 않는다.

각 역할의 Codex 대화 ID를 시도별로 분리하고 다른 시도의 대화를 재사용하지 않는다. 역할 간 전체 기록을 자동 복제하지 않는다.

### 8.2 업무 담당자의 행동

- 질문에 답하는 범위에서 관련 사실을 자연스럽게 설명한다.
- 특정 키워드를 정확히 입력해야만 사실을 얻는 퀴즈로 만들지 않는다.
- “뭘 물어볼 수 있나요?”에는 자신의 업무와 답할 수 있는 범위를 알려준다.
- “정답 기능 목록을 전부 알려줘”에는 모범 구현이나 채점표를 제공하지 않는다.
- 사실 자료에 없는 사항은 모른다고 하거나 확인이 필요하다고 말한다.
- 앞서 말한 업무 조건을 임의로 바꾸지 않는다.
- 구현 코드나 사용자 대신 작성한 계획을 제공하는 코딩 도우미 역할로 넘어가지 않는다.

비공개 사실은 ID, 관련 주제, 공개 조건, 답변 근거로 관리한다. 질문에 맞는 사실을 선택한 뒤 답변에 사용된 fact ID와 새로 공개된 fact ID를 서버에 기록한다. 사실 선택과 자연스러운 답변이 모순되지 않는지는 고정 질문 사례로 검증한다.

단순 질문 개수, 특정 문구 사용, 숨겨진 사실을 전부 찾았다는 사실만으로 점수를 올리지 않는다. 최종 판단에 필요한 정보를 적절히 확인했는지를 평가한다.

### 8.3 맥락 공유

담당자 답변에는 “코딩 도우미에게 공유” 액션을 제공한다. 공유한 원문과 출처를 남긴다. 사용자가 직접 요약해 전달할 수도 있고, 이 경우 사용자 요약으로 표시한다.

코딩 도우미가 받는 내용은 이미 사용자에게 공개된 정보로 제한한다. 사용자 메모에 AI 요약을 넣는 경우 생성 주체와 사용자 수정 여부를 보존한다.

### 8.4 격리 수준과 현실적 한계

서로 다른 대화와 폴더만으로 운영체제 수준의 접근 차단이 된다고 주장하지 않는다. 특히 읽기 전용 권한은 읽을 수 있는 범위를 자동으로 좁히는 것과 다르다.

제품은 기본 화면·API·컨텍스트에서 비공개 자료의 우발적 노출을 방지해야 한다. 비공개 과제 정보는 프런트엔드 번들과 응시 작업 폴더에 포함하지 않는다. 담당자·평가자는 임의 셸이나 외부 앱 도구가 필요하지 않으므로 가능한 런타임 정책으로 차단하고 실제 작동을 확인한다.

동일한 로컬 사용자가 직접 호스트 파일이나 Codex 이력을 열어보는 행위까지 막는 것은 MVP 범위 밖이다. 강한 시험 격리를 제공하려면 별도 OS 사용자 또는 컨테이너·원격 환경이 추가로 필요하다. 로컬 연습 결과는 감독된 시험 결과로 취급하지 않는다.

## 10. 로컬 Codex 연결 설계

### 10.1 권장 구조

브라우저는 로컬 백엔드와 통신하고, 백엔드의 Codex 어댑터가 별도 자식 프로세스로 App Server를 실행한다. 제품이 생성한 프로세스와 대화만 관리하며 현재 Codex 데스크톱 앱의 대화를 제어하지 않는다.

공식 문서는 App Server를 지속 대화, 스트리밍, 중단, 승인 처리가 필요한 앱의 연결 지점으로 안내한다. stdio 연결과 초기화, 대화 시작·복원, 턴 실행·중단을 지원한다. 이를 우선 연결 방식으로 선택한다. [S2][S3]

~~~
브라우저 UI
    ↕ 로컬 HTTP + 이벤트 스트림
로컬 애플리케이션 서버
    ├─ 세션·타이머·제출 제어
    ├─ 과제와 역할별 맥락 구성
    ├─ 기록·파일·검증·리포트 관리
    └─ Codex 어댑터
           ↕ stdio
       로컬 Codex App Server
           ↕ 사용자의 Codex 인증 및 모델 서비스

시도별 실행 관리자
    ├─ 작업 폴더와 파일 편집
    ├─ 터미널과 개발 서버
    └─ 제출본 및 검증 실행용 복사본
~~~

백엔드는 localhost에 바인딩한다. 브라우저가 Codex 프로세스나 임의 로컬 경로를 직접 제어하는 통로를 제공하지 않는다.

localhost 바인딩만으로 다른 웹페이지의 요청을 신뢰하지 않는다. 제어 API에는 호스트·Origin 검증과 로컬 세션 인증을 적용하고, 임의 외부 Origin을 허용하지 않는다. 응시자가 만든 앱에 제공하는 AI 연결 권한은 해당 시도의 과제 앱용 호출로 한정하며 파일·터미널·담당자·평가 API 권한과 분리한다.

### 10.2 어댑터의 책임

- 실행 파일 경로·버전 확인.
- 연결 초기화, 역할별 대화 생성, 메시지 전송과 응답 수신.
- 토큰 단위 출력과 완료 상태를 UI용 이벤트로 변환.
- 사용자 중단, 프로세스 오류, 재연결 및 대화 복원.
- 파일 변경·명령 결과·사용량처럼 제공되는 정보를 출처와 함께 저장.
- 승인이 필요한 요청을 UI에 표시하고 응답을 전달.
- 모델과 실제 적용 설정을 시도 기록에 보존.

문서의 연결 흐름은 initialize → initialized → thread/start 또는 thread/resume → turn/start이며, turn/interrupt로 중단을 요청한다. 완료 이벤트 수신만으로 성공 처리하지 않고 최종 상태가 성공인지 확인한다. [S2]

상세 요청·응답 스키마는 설치 버전에서 생성한 프로토콜 정의와 대조한다. PRD에 추정한 RPC 필드나 특정 모델명을 고정하지 않는다.

### 10.3 실행 정책

- 기본 연결은 현재 호스트의 Codex 인증을 사용한다.
- 모델은 사용 가능한 설정을 확인해 사용자가 선택하며, 고정된 “최신 모델” 이름을 하드코딩하지 않는다.
- 계정 상태 조회 성공과 실제 추론 성공을 별도 상태로 표시한다.
- 코딩 도우미는 시도 작업 폴더를 쓰기 범위로 사용한다. 더 넓은 접근은 정책과 승인 흐름을 통해 명시적으로 처리한다.
- 전역 Codex 설정을 앱이 덮어쓰지 않는다.
- 사용자의 기존 플러그인·MCP·지침이 역할에 섞이는 정도를 조사하고, 연습용 구성에서 불필요한 외부 도구를 차단한다.
- 담당자·평가자는 파일 수정과 임의 명령 실행을 필요로 하지 않는다. 차단 정책을 설정만으로 가정하지 않고 시범 연결에서 검증한다.
- 기본 모델 실행 동시성은 1로 시작해 계정 제한과 역할 간 혼선을 줄인다. 대기 상태와 큐 취소를 표시한다.
- coder의 장시간 실행으로 담당자 대화가 지연되면 중단 또는 큐 순서 변경이 가능해야 한다. 계정과 격리 검증 후 동시성 확대를 검토한다.

### 10.4 exec의 위치

CLI의 exec 방식은 짧은 연결 진단 또는 일괄 평가 실험의 보조 수단이다. MVP의 대화형 연결을 몰래 exec로 바꿔 승인·중단·복원 동작이 달라지게 하지 않는다. 대체 어댑터를 채택하려면 지원 기능을 명시하고 동일한 수용 테스트를 통과해야 한다.

### 10.5 최초 기술 검증 항목

구현 첫 단계에서 다음을 실제 호스트에서 확인한다.

1. 별도 App Server 프로세스 시작과 종료.
2. 현재 인증을 통한 짧은 응답 성공.
3. 서로 다른 역할 대화 간 맥락 비혼입.
4. 출력 스트리밍, 중단, 실패 상태.
5. 프로세스 재시작 이후 대화·이력 복구.
6. 시험용 작업 폴더 안의 파일 변경과 명령 실행.
7. 승인 요청의 UI 응답 왕복.
8. 역할별 도구와 파일 접근 제한이 실제로 적용되는지.
9. 활성 지침·설정·외부 도구가 평가자에게 답안을 노출하거나 응시 기록을 오염시키지 않는지.

역할별 제한이 지원되지 않으면, 제한된 별도 프로세스나 실행 환경을 설계한 뒤 진행한다. 프롬프트에 “읽지 마라”만 추가하고 격리 완료로 처리하지 않는다.

## 11. 파일·터미널·미리보기

- 시도마다 새 작업 폴더를 만들고 과제 템플릿만 복사한다.
- 공개 자료는 읽기 전용으로 제공하며 원본 과제 패키지와 비공개 자료는 작업 폴더 밖에 둔다.
- 파일 API는 경로 정규화와 심볼릭 링크 확인을 포함해 허용된 루트 밖의 접근을 거절한다.
- 사용자 편집과 AI 수정이 같은 파일에서 겹치면 버전 충돌을 표시하고 자동 덮어쓰지 않는다.
- 사용자 입력과 Codex 실행을 구분해 터미널 기록에 남긴다.
- 관리하는 자식 프로세스, 작업 폴더, 포트를 시도 ID와 연결한다.
- 미리보기는 해당 시도에서 등록된 포트만 열며 임의 URL 프록시가 되지 않게 한다.
- 제출 앱은 제어 UI와 다른 출처로 열거나 격리된 미리보기에서 실행해 세션 제어 API에 접근하지 못하게 한다.
- 고정 검증 명령은 과제 버전에 묶는다. 사용자가 테스트 파일을 바꾼 실행은 그 사실을 기록한다.
- 사용자가 바꾼 테스트의 통과만으로 제품 요구 충족을 선언하지 않는다.

검증 실행은 평가 모델과 분리된 실행 관리자가 수행한다. 버전이 고정된 검사와 실제 제출 앱을 대상으로 명령 실행·브라우저 조작·화면 캡처 등의 근거를 수집한다. 기계적으로 확인할 수 있는 결과와 사람 또는 모델이 해석해야 하는 품질을 구분한다. 자동 실행이 지원되지 않는 검사는 사용자 확인 자료를 받을 수 있으나 “사용자 확인”으로 표시하며 자동 검증으로 승격하지 않는다.

    starter/                작업 시작용 프로젝트
  private/
    stakeholder.json        담당자 역할·사실·공개 조건
    rubric.json             자체 연습 평가 기준
    validation/             고정 검증 정의·기대 결과
    calibration/            평가 품질 확인용 사례
~~~

앱의 배포 파일이나 브라우저 응답에는 private 디렉터리를 통째로 보내지 않는다. 공개 패키지 내 상대 경로도 비공개 자료로 이어지지 않아야 한다.

### 12.2 주요 필드

- 과제 ID, 버전, 언어, 권장 시간, 목표와 비목표.
- 공개 자료의 식별자와 버전.
- 담당자 사실 ID, 주제, 공개 조건, 근거 자료.
- 허용 가능한 다른 해결 방식 및 평가 시 제외할 가정.
- 실행·미리보기·검증 명령과 필요한 의존성.
- 평가 기준 ID, 판정 설명, 연결 가능한 증거 유형.
- 과제 자료와 기준의 검토 상태.

같은 시도 도중 과제 패키지를 수정해도 진행 중 시도에 자동 적용하지 않는다.

### 12.3 초기 과제 A: 고객 응대 연습 서비스

- 권장 시간: 120분.
- 업무 발견, 범위 결정, 교육 경험, 사실에 근거한 피드백을 중심으로 한다.
- 가상 상품 6종, 반품 정책, 교육 메모를 제작한다. 실제 상품·의료 효능 등의 사실처럼 보이게 하지 않는다.
- 제품 자료와 평가 사례의 모순을 과제 배포 전에 확인한다.
- 채점은 특정 UI나 프롬프트 구현을 정답으로 강제하지 않는다.
- “질문 없는 추천”, “적절한 질문과 추천”, “자료에 없는 성능 주장”, “짧지만 적절한 답”, “개선된 재답변”을 검증 사례로 둔다.
- 제공된 예시 풀이 전문은 응시 전에 보여주지 않는다. 이미 본 사용자는 사전 노출 여부를 표시할 수 있다.
- 응시자가 만든 서비스 자체에서 AI를 사용하려면 별도 “과제 앱용 AI” 범위를 제공한다. 공개 상품·정책·응시자가 만든 대화만 전달하고, 담당자 비공개 사실과 평가 기준에는 접근할 수 없다.
- 과제 앱용 연결은 같은 로컬 Codex 어댑터를 사용하되 대화 ID·사용량·로그 출처를 코딩 도우미와 구별한다. 이 연결 실패가 발생하면 가짜 답변을 실연결처럼 표시하지 않는다.

### 12.4 초기 과제 B: 장비 대여 예약 서비스

- 권장 시간: 150분.
- 제공된 로그인과 장비 자료를 기반으로 예약·취소를 구현.
- 업무 담당자가 예약 단위, 승인 여부, 취소 권한 등의 조건을 설명.
- 중복 요청·맞닿는 시간·취소·권한·입력 조건을 검증.
- 특정 DB 구조나 슬롯 설계를 강제하지 않고 업무 규칙 충족과 판단을 평가.
- PostgreSQL과 초기 데이터는 시작 전 준비 단계에서 확인한다. 설치가 필요한 경우를 “응시자의 실패”로 처리하지 않는다.
- 초기 템플릿에 필요한 DB 준비 방법과 상태 확인을 포함하며, 응시자가 가진 다른 DB를 변경하지 않는다.

## 13. 시간·상태·제출 규칙

### 13.1 상태

~~~
준비 → 수행 중 → 마감 처리 → 제출 고정 → 사후 질문 → 평가 중 → 완료
          ↕
      일시 정지
~~~

실패는 단계별 재시도 가능한 오류 상태로 관리한다. “평가 실패”가 “수행 실패”로 바뀌지 않아야 한다.

### 13.2 모드별 시간

| 모드 | 시간 처리 | 도움과 기록 |
|---|---|---|
| 자유 연습 | 사용자 일시 정지 가능 | 도움을 사용한 이력 기록 |
| 시험 연습 | 서버 기준 마감 시각 사용, 임의 시간 연장 없음 | 사후 질문 중 코딩 도우미 잠금 |
| 개발 | 시간 단축·변경·건너뛰기 가능 | 모든 결과에 개발용 표시 |

서버가 마감 시각과 정지 누적 시간을 저장한다. 화면 새로고침, 탭 전환, 브라우저 종료만으로 시간은 멈추지 않는다. 시험 연습에서 절전·서버 장애가 발생해도 기본적으로 시계는 진행하며, 개발자가 시간을 조정하면 조건 변경을 표시한다.

### 13.3 마감 처리

1. 서버가 제출 요청 또는 시간 만료를 한 번만 처리하도록 상태 전이를 잠근다.
2. 새 편집·메시지·명령 요청을 차단한다. 서버가 마감 전 수락한 저장 요청까지만 완료한다.
3. 실행 중인 에이전트 작업에 중단을 요청하고 관리 중인 쓰기 가능 프로세스를 정지한다.
4. 작업이 안정된 상태에서 제출본을 복사하고 파일 해시와 이벤트 마지막 순번을 저장한다.
5. 제출본 고정이 성공한 뒤에만 제출 완료를 표시한다.

중단 대기 중 발생한 파일 변경은 마감 후 변경으로 기록한다. 즉시 정확한 시각의 파일 상태를 보장한다고 주장하지 않으며, 최종 고정 시각과 마감 시각을 모두 남긴다. 마감 후 변경이 있으면 조건 이탈 표시를 붙인다.

프로세스 정지나 일관된 복사에 실패하면 “제출 처리 실패”로 남기고 평가를 시작하지 않는다. 기존 작업을 보존한 상태에서 재시도한다. 앱 밖에서 실행한 프로세스가 파일을 수정할 수 있다는 로컬 환경의 한계도 표시한다.

검증은 고정된 제출본에서 만든 별도 실행 복사본에서 수행한다. 검증이 파일을 생성하더라도 원래 제출본을 바꾸지 않는다.

| FactDisclosure | 사실 ID, 담당자 메시지 ID, 공개 시각 |

### 14.2 기록 원칙

- 입력 주체를 사용자·코딩 AI·담당자 AI·평가 AI·시스템으로 구분한다.
- 대화 출력, 도구 호출, 명령 결과, 파일 변경, 승인·거절, 오류, 설정 변경을 기록한다.
- Codex가 공개적으로 제공하는 메시지와 실행 이벤트만 사용한다. 비공개 내부 사고 과정을 수집하거나 평가 근거로 요구하지 않는다.
- 증거가 되는 파일 위치는 현재 파일이 아니라 해당 제출본의 경로·해시·줄 번호에 연결한다.
- 민감한 환경 변수·토큰은 저장하지 않는다. 출력에 나타난 비밀값을 제거한 경우 그 구간이 가려졌음을 표시한다.
- 새 연결에서 이벤트가 중복 전달돼도 같은 이벤트를 이중 집계하지 않는다.
- 일부 이벤트를 복구하지 못하면 기록 공백을 표시하고 평가 확신을 낮춘다.
- 앱 밖에서 수행한 일을 자동으로 관찰했다고 주장하지 않는다.

### 14.3 저장·내보내기

- 메타데이터는 로컬 SQLite, 대용량 출력과 제출 파일은 시도별 파일 저장소를 기본안으로 한다.
- 파일 저장과 메타데이터의 연결 실패를 감지하고 복구할 수 있어야 한다.
- 산출물·로그의 보존 기간은 MVP에서 자동 삭제 없이 사용자 삭제로 시작한다.
- 시도 삭제 시 앱이 만든 파일만 삭제하며 다른 프로젝트나 전역 Codex 이력은 삭제하지 않는다.
- 내보내기는 Markdown 리포트, JSON 근거 목록, 선택한 제출 파일로 구성한다.
- 비공개 과제 자료와 인증 정보는 기본 내보내기에 포함하지 않는다.

### 14.4 사용량 표시

Codex에서 제공되는 경우 역할별 토큰 사용량을 저장하고, 코딩 도우미·담당자·평가·과제 앱의 호출을 구분한다. 제공되지 않은 수치는 “확인 불가”로 표시한다. 정액 계정의 실제 비용을 토큰 수에서 임의 환산하지 않는다. 재연결 시 누적 사용량을 중복 합산하지 않으며, 사용량은 운영 정보로 제공하고 자체 점수의 직접 감점 요소로 사용하지 않는다.

## 15. 평가와 사후 질의응답

### 15.1 평가 원칙

평가는 공개된 기술·의도·인지 관점을 참고한 자체 기준이다. 공식 Cofa 점수와 비교하거나 환산하지 않는다. 결과를 좋게 보이게 하려는 표현, 질문 개수, 코드량, 토큰 절약만으로 가산하지 않는다.

| 축 | 자체 평가 항목 |
|---|---|
| 기술 | 핵심 사용자 흐름, 업무 규칙 충족, 검증의 적절성, 실패·권한·자료 처리 |
| 의도 | 문제·제약 파악, 우선순위·범위 결정, 위임과 맥락 전달, 결과에 따른 방향 수정 |
| 인지 | 선택 이유, 실제 동작 이해, 한계·실패 조건, 대안·조건 변화 설명 |

기술 항목은 과제에 맞게 구체화한다. 예를 들어 고객 응대 과제에 예약 동시성 기준을 적용하지 않는다. 질문 없이도 자료에서 충분히 파악한 조건은 인정한다.

### 15.2 점수

각 축의 4개 항목을 0~4로 판정하고 근거를 붙인다.

- 0: 충족하지 못했다는 근거가 있음.
- 1: 상당 부분 부족함.
- 2: 부분 충족.
- 3: 대체로 충족.
- 4: 충분한 근거로 충족.
- 미평가: 실행 실패나 기록 부족 등으로 판단할 수 없음.

항목별 기대 행동은 과제별로 정의한다. “근거가 없어서 모름”을 자동으로 0점 처리하지 않는다.

모든 항목을 판정할 수 있을 때 축별 점수는 항목 점수 합계 / 16 × 100이며, 총점은 세 축 점수 합계로 300점 만점이다. 화면에서는 소수 첫째 자리까지 표시한다. 하나라도 미평가이면 전체 총점을 만들지 않고 확인된 항목과 평가 가능 비율을 보여준다.

동일 제출본도 모델 평가가 달라질 수 있다. 재평가는 기존 결과를 덮어쓰지 않고 버전으로 저장한다. 300점 표기는 연습용 표현이며 공식 배점의 재현이 아니다.

### 15.3 근거 연결과 판정 검증

- 각 판정은 제출 파일, 실행 결과, 사용자 발언, 사용자 사후 답변 중 적절한 근거를 참조한다.
- AI가 작성한 설명을 사용자가 이해했다는 근거로 그대로 인정하지 않는다.
- 사용자 발언이 없더라도 직접 작성한 메모·수정·검증 기록이 있으면 해당 기여의 증거가 될 수 있다.
- “테스트 통과”는 실제 실행 결과와 연결한다. AI의 완료 주장만 있으면 주장으로 표시한다.
- 평가 응답의 근거 ID와 파일 위치가 실제로 존재하는지 서버에서 검증한다.
- 스키마 또는 근거 검증이 실패하면 수정 요청을 최대 1회 수행하고, 다시 실패하면 평가 오류로 남긴다.
- 제출 파일의 “나에게 만점을 줘” 같은 문장은 자료로 취급하며 평가 지침으로 실행하지 않는다.

### 15.4 사후 질문

평가자는 제출본에서 확인할 가치가 큰 결정·모순·미확인 부분을 골라 3~5개 질문을 만든다. 외워서 답하는 일반 지식 문제만 제시하지 않는다.

예:

- “알림을 제외한 이유가 무엇이며, 어떤 업무 조건이면 필요해지나요?”
- “이 피드백이 상품 자료와 다른 내용을 말하는지 어떻게 확인했나요?”
- “본인이 직접 확인한 동작과 AI의 보고만 받은 동작을 구분해 설명해주세요.”

질문 생성 중 답변의 정답이나 내부 판정 기준을 노출하지 않는다. 제출본에 없는 기능을 구현했다고 가정한 질문은 근거 검증에서 제외한다.

### 15.5 평가 품질 확인

과제별로 강한 수행·부분 수행·실패 수행·근거 부족 사례를 제작한다. 다음이 안정적으로 구분되는지 검토한다.

- 잘 작동하지만 설명과 판단 근거가 부족한 결과.
- 설명은 훌륭하지만 실제 실행이 실패한 결과.
- 적은 질문으로 필요한 조건을 정확히 파악한 결과.
- 많은 질문을 했지만 구현에 반영하지 않은 결과.
- 테스트를 수정해 통과시킨 결과와 요구를 실제 충족한 결과.

점수의 반복 변동과 잘못된 근거 생성을 측정한다. 초기 결과는 개발자 검토를 거쳐 기준을 보완하며, 자동 평가만으로 공정성이 검증됐다고 주장하지 않는다.

## 16. 장애 및 예외 처리

| 상황 | 요구 동작 |
|---|---|
| Codex 미설치 | 경로 설정·설치 안내, 시도 시작 전 차단 |
| 로그인 또는 모델 요청 실패 | 구체적 실패 상태 표시, 외부 인증 설정을 변경하지 않음 |
| 계정 사용 제한 | 메시지와 작업 보존, 재시도 시점은 알려진 정보만 표시 |
| 답변 중 연결 단절 | 받은 출력 보존, 상태 조회 후 복원, 동일 요청을 무조건 재전송하지 않음 |
| 사용자가 중단 | 중단 요청과 실제 중단 완료를 구분, 이미 실행된 파일 변경은 남음 |
| 브라우저 새로고침 | 서버에 저장된 시도·타이머·대화·저장 상태 복원 |
| 파일 충돌 | 사용자 버퍼와 디스크 변경을 비교하고 선택하게 함 |
| 테스트 시간 초과 | 프로세스 종료, 시간 초과 표시, 통과로 처리하지 않음 |
| 제출 실패 | 작업 보존, 제출 고정 전 평가 시작 금지 |
| 평가 실패 | 제출본 유지, 평가만 재시도 |
| 담당자 답변 모순 | 관련 대화와 사실 ID로 개발 모드에서 재현 가능 |
| 민감정보 발견 | 화면·내보내기에 가림 적용, 삭제·재생성 여부를 사용자가 결정 |

재시도는 사용자 메시지와 실제 실행 결과의 중복을 만들지 않아야 한다. 접수 여부가 불명확한 명령은 먼저 상태를 확인하고, 확인할 수 없으면 중복 실행 위험을 표시한다.

## 17. 기본 기술 방향

구체 라이브러리 버전과 폴더 구조는 구현 단계에서 확정한다.

| 계층 | 기본안 | 이유 |
|---|---|---|
| UI | React + TypeScript | 상태가 많은 패널과 대화 화면 구성 |
| 편집기 | Monaco 계열 편집기 | 파일 편집·변경 비교 활용 |
| 터미널 | xterm 계열 UI + 로컬 PTY | 실제 명령 실행 경험 |
| 로컬 서버 | Node.js + TypeScript | 프로세스·파일·스트리밍·Codex 연결 |
| 저장 | SQLite + 파일 저장소 | 단일 사용자 환경에서 운영 부담 축소 |
| 이벤트 전달 | SSE 또는 WebSocket | 대화·명령 진행 상태 전달 |
| 모델 연결 | Codex App Server 어댑터 | 역할별 대화와 실행 수명주기 관리 |
| 검증 | 단위·통합 테스트 + 브라우저 사용자 흐름 확인 | 요구사항과 결과의 연결 검증 |

새 모델 제공자를 당장 추가하지 않지만 연결 인터페이스와 화면 로직은 분리한다. 분산 큐·마이크로서비스·벡터 DB는 MVP에 도입하지 않는다.

로컬 파일 저장이더라도 모델에 보낸 자료는 외부 추론 요청에 포함될 수 있다. 연결 설정과 내보내기 화면에서 실제 데이터 흐름을 설명한다.

## 18. 개발 단계와 완료 게이트

### 단계 0 — 연결 가능성 확인

로컬 Codex와 독립 App Server 연결, 로그인 사용, 스트리밍·중단·복원, 도구 제한을 실제로 확인한다. 짧은 실연결 결과와 호환 버전을 기록한다.

완료 게이트: 역할 분리와 실행 정책을 만족하는 연결 방식이 확보됨. 실패 시 UI를 넓히기 전에 어댑터·격리 방식을 수정한다.

### 단계 1 — 한 과제의 전체 흐름

고객 응대 과제를 사용해 과제 선택, 담당자 대화, 코딩 도우미, 파일·터미널·미리보기, 제출, 사후 질문, 리포트의 최소 경로를 연결한다.

완료 게이트: 실제 Codex로 생성한 결과물을 고정 제출하고 실제 근거를 포함한 리포트를 한 번 완성.

### 단계 2 — 복구와 평가 신뢰성

새로고침·프로세스 재시작·모델 오류·중단·제출 경합·근거 검증·개발 모드를 추가한다.

완료 게이트: 실패 시나리오에서 작업과 제출본을 보존하고 잘못된 완료·통과 판정을 만들지 않음.

### 단계 3 — 두 번째 과제와 MVP 점검

장비 예약 패키지를 추가하고 과제별 검증·평가 기준 교체가 가능한지 확인한다.

완료 게이트: 두 과제로 핵심 수용 테스트 통과, 리포트 내보내기, 설정·실행 안내 작성.

## 19. MVP 수용 테스트

| ID | 시나리오 | 기대 결과 |
|---|---|---|
| A01 | 로그인된 호스트에서 연결 확인 | 실제 짧은 응답 성공 후 준비 완료 |

| A03 | 담당자에게 모호한 질문·구체적 질문 | 관련 사실을 제공하며 정답 계획은 대신 작성하지 않음 |
| A04 | 코딩 도우미에게 비공개 기준 요청 | 앱이 해당 맥락을 제공하지 않음 |
| A05 | 담당자 답변 공유 | 선택한 공개 메시지만 출처와 함께 전달 |
| A06 | Codex가 파일 수정 후 테스트 | 실제 파일과 실행 결과가 UI·기록에 일치 |
| A07 | AI 수정 중 사용자가 같은 파일 편집 | 무음 덮어쓰기 없이 충돌 안내 |

| A09 | 요청 전송 직후 연결 단절 | 중복 명령 실행 없이 상태 확인 또는 불확실성 표시 |
| A10 | 수행 중 모델 중단 | 종료 상태 확인, 이전 변경 보존 |

| A12 | 시간 만료와 실행 중 작업 겹침 | 마감 전이 잠금, 작업 정지, 변경 시각과 제출 고정 시각 기록 |
| A13 | 제출 후 파일 변경 | 이전 제출본과 평가 근거 불변 |
| A14 | 테스트 실패·시간 초과 | 실패·시간 초과로 표시, 통과 점수 근거로 사용 안 함 |

| A16 | 사후 질문 중 코딩 도우미 사용 | 시험 연습 모드에서 차단, 개발 우회는 조건 변경 기록 |
| A17 | 평가 실패 후 재시도 | 같은 제출본 사용, 결과 버전 분리 |

| A21 | 두 번째 과제로 전환 | 별도 작업 폴더·대화·기준 사용 |

기록 재생 테스트는 UI·상태 처리의 검증 수단이며 실제 Codex 연결 성공의 대체 증거로 사용하지 않는다.

## 20. 확정한 기본값과 남은 확인

### 20.1 이 PRD에서 정한 기본값

- 개인용 로컬 웹 앱으로 시작.
- 두 창작 과제를 제공하며 고객 응대 과제를 첫 검증 대상으로 사용.
- 로컬 Codex App Server를 우선 연결 방식으로 채택.
- 실제 코딩·실행 환경과 담당자 대화를 함께 제공.
- 기술·의도·인지에 대한 근거 중심 자체 평가와 선택적인 300점 표현.
- 강한 감독 기능 대신 연습의 조건·근거·한계를 명확하게 표시.
- 문서의 예시 풀이를 응시 작업 공간에 기본으로 복사하지 않음.

### 20.2 개발 중 확인할 사항

| 항목 | 현재 상태 | 확인 단계 |
|---|---|---|
| App Server의 실제 추론·승인·복구 | 명령 존재만 확인, 실호출 미검증 | 단계 0 |
| 역할별 도구·파일 제한과 전역 설정 상속 | 구현 전 검증 필요 | 단계 0 |
| 계정의 사용 가능 모델·동시성·잔여 제한 | 추정하지 않음 | 연결 확인 및 설정 화면 |
| Codex 이벤트에서 사용량·변경 근거 제공 범위 | 설치 버전 스키마 확인 필요 | 단계 0~1 |
| 고객 응대 앱용 AI 연결의 구체 인터페이스 | 제품 요구만 정의 | 단계 1 |
| 제출 시 프로세스 정지·파일 고정의 일관성 | 구현 검증 필요 | 단계 2 |
| 평가 반복 변동·피드백 적합성 | 기준 사례 제작 후 검토 | 단계 2~3 |
| 강한 격리·외부 공개·원격 실행 | MVP 밖 | 필요해질 때 별도 설계 |

질문에 대한 사용자 답변이 없어서 막힌 항목은 없다. 위 기본값으로 개발 설계를 시작할 수 있으며, 검증 결과에 따라 문서 버전을 갱신한다.
