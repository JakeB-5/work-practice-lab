| 태스크 | 내용 | 준비된 자료 | 착수 범위 |

## 2. 네 개의 작업 흐름으로 운영하는 예

| 흐름 | 주 담당 | 공통 계약 이후 | 통합 시 전달물 |
|---|---|---|---|
| A | 플랫폼·Codex | T02~T04, T09 | 실행 가능한 API, 이벤트, 마감·제출 |
| B | 작업 공간·검증 | T07, T10 | 파일/PTY/preview, 검증 근거 |
| C | UI | T08, T12 | 재생·실연결을 모두 지원하는 화면 |
| D | 콘텐츠·역할·평가 | T05, T06, T11 | 과제 패키지, 담당자 사실, 판정 |

같은 흐름이 큰 작업을 전부 동시에 수행하는 계획은 아니다. 카드의 선행 조건을 따른다.
개발 병렬화와 제품 안의 추론 동시성은 다르다. 제품의 기본 최대 동시 추론은 1이다.

## 5. 게이트와 완료

- **G-RUNTIME:** T00.06. 스키마 필드 존재와 실제 모델·권한·복원 성공을 구분한다.
- **G-CONTRACT:** T01.05. runtime 결과를 반영하고 계약·fixture 호환성을 고정한다.
- **G-FIRST:** T14.01. 고객 응대 과제를 실제 Codex로 처음 끝까지 완료한다.
- **G-MVP:** T14.05. 90개 P0 작업의 검증과 두 과제의 수용 조건을 만족한다.
- P1 6개와 후속 2개는 G-MVP 완료 조건에 포함하지 않는다.

## 6. 충돌 방지

- packages/contracts와 DB migration은 공통 담당이 소유한다.
- Codex wire를 직접 쓰는 코드는 packages/codex-adapter에만 둔다.
- UI는 public DTO만 받고 private package를 import하지 않는다.
- 제출 상태는 서버 coordinator만 변경한다.
- 과제 A/B는 각자 디렉터리를 소유하며 shared starter 변경은 합의한다.
- Spec 변경이 필요하면 관련 schema·fixture·task dependency를 함께 바꾼다.
- 이 원장은 진행을 자동 실행하거나 에이전트를 이미 배정한 기록이 아니다.
